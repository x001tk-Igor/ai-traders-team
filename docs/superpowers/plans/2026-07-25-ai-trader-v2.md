# ИИ-трейдер v2: алертная архитектура + перенос элементов Qwen — Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** довести `ai-trader-skillset` до системы, в которой **модель наблюдает и решает всё**, код обслуживает её органами чувств, памятью и двумя предохранителями, а внимание модели тратится только на события, которые она сама объявила важными.

**Architecture — алертная петля.** Модель заканчивает каждый цикл записью `alerts.json` — условий, по которым её следует разбудить. `alert_watch.py` запускается через `Monitor` (или `Bash run_in_background`) внутри той же сессии Claude Code, сравнивает числа с порогами модели и печатает строку **только при срабатывании** — эта строка асинхронно будит модель и приносит с собой готовый снимок. Пока условия молчат — расход токенов нулевой. Скрипт не имеет ни одного собственного торгового правила: он датчик, а не водитель. Единственное исключение — **стоп-кран**: две стены (−3% день / −6% всего), где он действует сам, потому что у этих чисел нет альтернативной трактовки.

**Что сознательно НЕ автоматизируется.** BE, частичные фиксации, трейлинг, time-stop, invalidation — всё это приходит модели как алерт, и решение принимает она. Контекст между входом и точкой выхода мог измениться; автоматика фиксировала бы слепо.

**Tech Stack:** Python 3.10+, MetaTrader5, pandas/numpy, pytest. Офлайн-тесты на `FakeMarket` без живого MT5. Harness: Claude Code (`Monitor` / `Bash run_in_background`). Windows Server, PowerShell.

**Model-agnostic by design.** ~70% пакета — Python и файлы, от модели не зависят. Различия между Anthropic / Qwen / GLM / Kimi сводятся к одной строке конфига (`model_profile`) и приёмочному тесту (`model_smoke.py`). Один пакет, не два.

**Исполнители:** **я** = Claude в этой сессии (код + офлайн-тесты). **ты** = владелец счёта (зонды на живом MT5, смоук, выкат, кросс-модельная приёмка в самом конце).

**Условие:** система на ПК трейдера уже торгует. Все изменения аддитивны; схема журнала расширяется обратно совместимо (нет поля → `"unknown"`). Торговлю останавливаем только на окно выката (Ф9).

приказа, отправленного руками из GUI терминала, `MOBILE` — из мобильного,

смотрит поле «Причина» (серверные логи брокера, отчёты, выгрузка истории с этим

обходом контроля брокера — не делаю и не рекомендую.

### Task 4.2: атомарный вход

**Файлы:** Create `scripts/enter.py`, Create `tests/test_enter.py`

> **Сделка не должна выглядеть машинной — это требование, а не пожелание.**
> Идеально круглые лоты во всех сделках (0.10 / 0.50 / 1.00) и одинаковая
> дистанция стопа — характерный след советника, не менее заметный, чем `magic`.
> Хорошая новость: **так уже получается само.** `size_position.compute_lots`
> считает лот из риска и делает `floor` к шагу, поэтому значения выходят
> некруглыми естественным образом; дистанция стопа приходит от модели по
> структуре рынка, а не константой. **Задача — не испортить это:** не вводить
> округление «для красоты», не подгонять лот к круглому, не подставлять
> фиксированную дистанцию стопа по умолчанию. Покрой тестом, что при разных
> входных риске и дистанции стопа лоты получаются разные и не круглые.
> Переделать это после накопления истории сделок будет нельзя — история уже
> будет выглядеть машинной.

Порядок строгий:

```
1. entry_gate (Ф5) → DENY? стоп с причиной
2. quality: costs_R ≤ max; breakeven_p vs p_win_journal → DENY? стоп
3. profile: weak → planned_only, только подтверждённые, риск ×0.5
4. size: compute_lots × status_mult × profile_mult → 0? стоп
5. validate_decision → неполно? стоп (ДО отправки)
6. append_decision в журнал — **`trade_id` ОБЯЗАН быть `str(ticket)` брокера**
7. place_order + пост-проверка SL
8. ордер не прошёл → append_outcome {exit_reason:"aborted", R:0}
9. успех → обновить alerts.json: снять сработавший триггер,
   поставить алерты ведения (pos-1r, pos-stall, invalidation-уровень)
```

> ⚠️ **Двухфазная запись — решение принято, не изобретай своё.**
>
> `trade_id` обязан быть `str(ticket)`: на этом стоят обе стороны сверки с
> брокером — дописывание исходов (`reconcile` сопоставляет с `position_id` из
> истории) и детект orphan (`find_orphans` — с `ticket` открытой позиции). Но
> тикет известен только ПОСЛЕ `order_send`, а следа в журнале нельзя не оставить
> ДО отправки. Маркеры в ордере (`magic`/`comment`) для связи **запрещены** —
> сделка должна выглядеть ручной.
>
> Поэтому порядок такой:
> ```
> append_intent(intent_id=…, все параметры, тезис, риск)   ← ДО отправки
> place_order(...)                                         ← тикет в результате
> append_decision(trade_id=str(ticket), intent_id=…)       ← тикет уже известен
> ```
> Что это даёт на каждом стыке сбоя:
> - упало между intent и отправкой → intent есть, позиции нет → при старте помечается несостоявшимся;
> - упало между филлом и decision → intent есть, позиция есть → **decision достраивается автоматически из intent + тикет**, ничего не потеряно;
> - позиция без intent и без decision → это **не наша** сделка (ручная у владельца счёта или второй агент) → `HALT_NEW`, не трогать.
>
> Инвариант «нет ордера без следа» сохранён, различение своего и чужого получается
> из журнала. Цена — одна лишняя запись на сделку.
>
> **Обязательные тесты:** своя сделка не определяется как orphan; падение между
> филлом и `append_decision` восстанавливается из intent; intent без позиции
> помечается несостоявшимся.
>
> Требует расширения `journal.py`: тип записи `intent` + `INTENT_REQUIRED`, и
> `intent_id` в `DECISION_OPTIONAL`. Схему решения (28 обязательных полей) не менять.
