# Контракт `alerts.json` и `ctx` (задача 3.1)

Реализация: `trader_lib/alerts.py`. Тесты: `tests/test_alerts.py`.

Этот документ — контракт для задачи 3.2 (датчик `alert_watch.py`): она обязана
собрать `ctx` в описанной здесь форме и вызывать `evaluate()` каждый тик.
Задача 3.1 (этот модуль) НЕ читает MT5, НЕ пишет журнал, НЕ содержит цикла
опроса — только чистые функции.

## Зачем: алертная петля

Модель работает по подписке — её внимание дорого. Вместо непрерывного цикла
модель в конце сессии пишет `alerts.json` — условия, по которым её следует
разбудить. Датчик крутится раз в секунду, читает файл, зовёт `evaluate()`
и печатает строку **только при срабатывании**. Пока условия молчат — расход
нулевой. `evaluate()` — не водитель, а датчик: она не принимает торговых
решений, только сравнивает числа из `ctx` с порогами, которые задала модель.

## Файл `alerts.json`

```json
{
  "version": 1,
  "written_by": "claude-opus-5",
  "written_utc": "2026-07-27T06:02:11Z",
  "expires_utc": "2026-07-27T16:00:00Z",
  "alerts": [
    {"id": "h1-trigger", "symbol": "XAUUSD", "type": "price_below",
     "level": 2415.0, "once": true, "priority": "normal",
     "note": "гипотеза H1: возврат под уровень → смотрю вход в шорт"}
  ]
}
```

Универсальные поля алерта (все, кроме `id`/`type`, необязательны):

| поле | по умолчанию | смысл |
|---|---|---|
| `id` | — (нужен для трассировки состояния; без него подставляется `<no-id-N>`) | |
| `type` | — | один из 18 типов ниже |
| `symbol` / `ticket` | — | смотря по типу |
| `once` | `false` | разоружиться после срабатывания |
| `rearm_after_minutes` | `null` | перевооружиться через N минут после срабатывания |
| `priority` | `"normal"` | `"normal"` подчиняется дневному лимиту и обычному интервалу; `"critical"` обходит ТОЛЬКО дневной лимит, свой (короче) интервал и общий абсолютный потолок — нет |
| `note` | `null` | текст для модели, попадает в `fired[i]['note']` без изменений |

### `load_alerts(path, *, now) -> dict`

- Файла нет → `{"version":1,"written_by":None,"written_utc":None,"expires_utc":None,"alerts":[]}`,
  **не исключение**: датчик обязан работать до первой записи модели.
- `expires_utc` в прошлом относительно `now` → **весь файл** отбрасывается
  (тот же пустой набор), не только "просроченные" алерты по отдельности:
  в контракте нет per-алертного `expires`, есть только файловый — это метка
  "я обещала вернуться до этого момента", а не срок годности каждого условия.
- Отсутствующий/пустой `expires_utc` → алерты не истекают.
- Битый JSON **не перехватывается** — исключение долетает до вызывающего.
  Это осознанно: `write_alerts_atomic` существует именно для того, чтобы
  такого не случалось на штатном пути (запись через temp-файл + `os.replace`);
  тихо проглатывать порчу контракта значило бы прятать реальный баг.

### `write_alerts_atomic(path, data)`

Пишет во временный файл в той же директории, `fsync`, затем `os.replace`
(атомарно и на POSIX, и на Windows — в отличие от `os.rename`, который на
Windows падает, если целевой файл уже существует). Датчик опрашивает файл
раз в секунду и не должен увидеть частично записанный JSON.

`data` обязан быть JSON-сериализуемым **как есть** — все временные метки
внутри уже ISO-строки, не объекты `datetime` (то же соглашение, что и в
`journal.py`: вызывающий форматирует `ts` до записи).

## `evaluate(alerts, ctx, *, now, budget) -> (fired, updated_alerts)`

Чистая функция. `alerts` — то, что вернул `load_alerts` (или предыдущий
`evaluate`). `budget` — обычно результат `event_budget(...)`.

**`fired`** — список того, что сработало на этом тике:
```python
{"id": ..., "type": ..., "symbol": alert.get("symbol"), "ticket": alert.get("ticket"),
 "priority": ..., "note": alert.get("note"), "fired_utc": "2026-...", "detail": {...}}
```

**`updated_alerts`** — та же структура, что `alerts`, плюс:
- `alerts`: список с обновлённым `_state` на каждом элементе (см. ниже);
- `skipped`: `[{"id", "type", "reason"}]` — что НЕ сработало из-за нехватки
  данных в `ctx`, малформированного алерта, разоружения или исчерпанного
  бюджета. Обычное "условие пока ложно" в `skipped` **не** попадает — это
  штатное ожидание, а не диагностический случай.

Вызывающий (задача 3.2) обязан передать `updated_alerts` в
`write_alerts_atomic` после каждого тика — иначе состояние разоружения живёт
только в памяти процесса датчика и теряется при его перезапуске.

### Хранение состояния: поле `_state`

Каждый алерт в `updated_alerts["alerts"]` получает служебное поле `_state`
(зарезервированный префикс, не часть словаря модели):

```python
{"armed": true, "last_fired_utc": "2026-07-27T10:00:00+00:00", "remember": <любое>}
```

- `armed` — вооружён ли алерт сейчас.
- `last_fired_utc` — ISO-время последнего срабатывания (для расчёта rearm).
- `remember` — память типов с "флипом" (`trend_flips`, `gate_verdict_changes`,
  `session_phase_changes`): предыдущее наблюдённое значение.

Состояние живёт **внутри самого алерта**, не в отдельном файле, и путешествует
вместе с `alerts.json` через `write_alerts_atomic`/`load_alerts`. Когда
**модель** в конце следующей сессии перезаписывает файл свежим набором условий
— `_state` у новых записей естественно отсутствует, и это **намеренный
сброс**: новый цикл наблюдения начинается с чистого листа, а не наследует
разоружение прошлых гипотез. Когда **датчик** перечитывает файл между своими
же тиками (не модель) — состояние обязано пережить это чтение/запись; тест
`test_state_resets_when_model_rewrites_file` фиксирует оба случая явно.

### Развилка: `once` vs `rearm_after_minutes`

Табличное описание в задаче звучит как два независимых переключателя, но
буквальное прочтение ("once → разоружается", "rearm_after_minutes → снова
вооружается") оставляет дыру: пример `vol-regime` в задаче использует
`rearm_after_minutes` **без** `once` — если бы разоружение включал только
`once`, у этого алерта не было бы что перевооружать, и он бы спамил каждый
тик, пока `atr_pctile > 0.9`.

Принятое решение — разоружение на срабатывании включается, если задан
**либо** `once=true`, **либо** `rearm_after_minutes` (сам факт, что у алерта
есть таймер перевооружения, подразумевает, что ему есть что перевооружать):

```python
disarms_on_fire = once or (rearm_after_minutes is not None)
```

- `once=true`, без `rearm_after_minutes` — разоружение постоянное, до
  перезаписи файла моделью.
- `rearm_after_minutes=N`, без `once` — разоружение временное, авто-
  перевооружение через N минут после `last_fired_utc`.
- оба заданы — `rearm_after_minutes` управляет перевооружением; `once`
  избыточен, но не противоречит.
- ни один не задан — алерт **не разоружается вовсе** и участвует в проверке
  условия на каждом тике, пока оно истинно. Единственное, что тогда сдерживает
  повтор, — событийный бюджет (`event_budget`, см. ниже). Это ОСОЗНАННО
  ДОПУСТИМЫЙ, а не запасной режим — но с важной оговоркой, добавленной после
  инцидента (см. следующий раздел): такой алерт **не** превращается в "одно
  событие", он превращается в "напоминания с частотой интервала своего яруса".
  Модель, ставящая `spread_anomaly`/`gap` с `priority: "critical"` и без
  `once`/`rearm`, получит повторные пробуждения раз в
  `min_seconds_between_critical_events` (по умолчанию 15с), пока аномалия
  длится — это ожидаемо и нужно для критических состояний, но это НЕ "одно
  срабатывание", и модель должна закладывать именно такое поведение, ставя
  такой алерт.

### Инцидент: `critical` обходил бюджет целиком, а не только дневной лимит

Первая версия `evaluate()` трактовала `priority: "critical"` как "игнорирует
`budget` целиком" — единственная защита от повтора у critical-алерта без
`once`/`rearm` была в его собственном условии (перестанет быть истинным).
Зонд на реальном конфиге (`spread_anomaly` без `once`/`rearm`, десять тиков
по секунде, спред остаётся аномальным) показал: **10 срабатываний за 10
секунд**. Аномалия спреда или пробитая стена держатся минутами, а датчик
опрашивает раз в секунду — то есть десятки событий в минуту. `Monitor`,
через который датчик будит модель, **автоматически останавливается при
переборе событий** — весь контур пробуждения умирал именно в момент
аномалии, когда модель нужна больше всего. Намерение "critical должен
будить всегда" было верным, но "всегда" ≠ "каждую секунду": разбудить один
раз и разбудить шестьдесят раз — разница между работающей системой и
остановленной.

Исправление — три независимых яруса вместо одного плоского флага (детали
и мотивация каждого — в `event_budget` ниже):
1. **normal**: дневной лимит `max_events_per_day` И обычный интервал
   `min_seconds_between_events`.
2. **critical**: обходит ТОЛЬКО дневной лимит normal. Свой интервал
   `min_seconds_between_critical_events` (короче обычного, т.к. критическое
   нельзя откладывать на минуту) он обязан соблюдать.
3. **абсолютный потолок** `max_events_per_minute` — общий для normal и
   critical, не обходит никто. Он защищает не квоту модели, а сам механизм:
   несколько РАЗНЫХ critical-алертов могут стать истинными ОДНОВРЕМЕННО, в
   один и тот же тик — ни дневной лимит, ни интервал (оба меряют время ОТ
   ПРЕДЫДУЩЕГО события) не защищают от одновременной пачки, когда
   предыдущего события ещё не было. `evaluate()` расходует
   `hard_cap_remaining` по одному на каждое фактическое срабатывание СРАЗУ
   внутри одного вызова — пачка из нескольких одновременно истинных
   critical-условий в одном тике тоже упирается в потолок, а не проходит вся.

Регрессионный тест — `test_critical_repeated_ticks_bounded_by_interval_and_
hard_cap` в `tests/test_alerts.py`: воспроизводит зонд коллеги дословно
(десять тиков по секунде, истинное критическое условие, реальная
последовательность `event_budget()` → `evaluate()` → `event_budget()` →
...) и проверяет ВЕРХНЮЮ ГРАНИЦУ числа срабатываний, а не один вызов —
одиночный вызов не отличает "интервал применён" от "интервал проигнорирован",
если событие всего одно.

### Развилка: как детектится "пересечение уровня"

`price_above`/`price_below` в таблице задачи описаны как "цена **пересекла**
уровень", что звучит как edge-detection (нужна память предыдущей цены).
Решение: **edge-detection не реализована**, условие — простое сравнение
`price > level` / `price < level` на каждый тик. Защита от повторного
срабатывания, пока цена остаётся по ту же сторону уровня, обеспечивается
существующими механизмами — `once`/`rearm_after_minutes` (для конкретного
алерта) и событийным бюджетом (глобально) — а не отдельной памятью цены.
Это проще, не требует дополнительного состояния и покрывает тот же случай:
модель, которая хочет "разбудить один раз, когда пробьёт", ставит `once:true`.

Три типа, которым **действительно** нужна память предыдущего значения —
`trend_flips`, `gate_verdict_changes`, `session_phase_changes` — хранят её
в `_state.remember` (см. выше) именно потому, что их условие — "изменилось
относительно прошлого", а не "число относительно порога", и без запомненного
значения "изменилось" не определить в принципе. **Первое наблюдение** такого
алерта (когда `remember` ещё `null`) не срабатывает — оно устанавливает
эталон для сравнения, сравнивать пока не с чем.

### Развилка: несуществующий/закрытый `ticket`

`ctx["positions"]` содержит только **открытые** позиции, ключ — номер тикета.
Если тикет из алерта отсутствует в `ctx["positions"]` (закрылась, никогда не
существовала, опечатка модели) — это трактуется **так же, как отсутствие
любых других данных**: алерт не срабатывает и попадает в `skipped` с причиной
`"нет данных по позиции <ticket>..."`. Никакого специального кода ошибки —
единообразие с общим правилом "нет данных → skip" проще и не создаёт второго
пути для похожего по сути случая.

### Псевдо-торговая логика вынесена из `evaluate()` в `ctx`

Типы `gap`, `sl_jumped`, `data_stale` в таблице задачи не имеют собственного
числового порога как поле алерта (в отличие от, скажем, `spread_anomaly.mult`
или `price_above.level`). Если бы `evaluate()` сама решала, что такое "разрыв"
или "тик устарел", ей пришлось бы держать константы-пороги внутри себя — то
есть протаскивать торговое/операционное суждение в модуль, которому это
запрещено. Решение: для этих трёх типов `ctx` несёт уже посчитанный **bool**
(`sym["bar_gap"]`, `pos["beyond_sl"]`, `sym["tick_stale"]`), а `evaluate()`
только читает его. Пороги (за сколько секунд тик считается устаревшим, что
считать разрывом бара) — забота задачи 3.2/perceive, не этого модуля.

`spread_anomaly`, наоборot, **имеет** числовое поле (`mult`) — сравнение
`spread_points > mult * spread_median_points` делает сама `evaluate()`,
потому что это чистая арифметика над готовыми числами `ctx` и порогом
модели, а не суждение "что считать аномалией".

### Устойчивость к плохим данным

- Неизвестный `type` → `skipped`, не исключение.
- Известный `type` без обязательного поля (например, `price_above` без
  `level`) → `skipped` с именами недостающих полей, не исключение: это ввод
  модели (её JSON), а не конфиг кода — тот же принцип, что и в `quality.py`
  для нераспознанных `status`/`profile`.
- Неизвестный `priority` (не `"normal"`/`"critical"`) → `skipped`, алерт НЕ
  срабатывает в этом тике. Он **не** тихо трактуется как `"normal"`: если бы
  трактовался, опечатка вроде `"critcal"` вместо `"critical"` тихо получила
  бы поведение normal (не страшно), но по тому же принципу опечатка в другую
  сторону не должна иметь шанс тихо стать "critical" и обойти бюджет — прямой
  запрет обеих трактовок проще и симметричнее, чем угадывать намерение.
- Любое исключение внутри вычисления условия конкретного типа (например,
  `level` — строка, а не число) перехватывается и превращается в `skipped`
  с текстом ошибки — один кривой алерт не роняет весь тик датчика,
  который крутится раз в секунду.

## Форма `ctx`

`ctx` — снимок восприятия на этот тик, собирает его задача 3.2 (сенсор). Он
**не** проходит через `load_alerts`/`write_alerts_atomic` и не обязан быть
JSON-сериализуемым — временные метки внутри это нативные `datetime` (tz-aware,
UTC), а не строки. Отсутствие ключа и `None`-значение трактуются одинаково —
как "не знаю"; это то же правило, что в `features.py`/`exposure.py`
(недостаток данных → `None` + `reason`, никогда угадывание).

```python
ctx = {
    "symbols": {
        "XAUUSD": {
            "price": 2415.3,              # float|None — цена для price_above/below/touch
            "atr": 3.2,                   # float|None — ОДНО эталонное значение ATR
                                           #   (не по ТФ: ни один тип, кроме trend_flips,
                                           #   не указывает ТФ в своих полях)
            "atr_pctile": 0.72,            # float|None — ЭТАЛОННЫЙ ATR-перцентиль [0,1]
            "atr_pctile_by_tf": {          # перцентиль по каждому ТФ: алерт
                "M5": 0.72, "H1": 0.31},   # может назвать свой явно полем tf
                                           #   (тоже ОДНО значение, не по ТФ — см. предложение ниже)
            "trend": {"H1": "up", "M15": "flat"},  # {tf: "up"|"down"|"flat"|None} — ПО ТФ,
                                           #   т.к. trend_flips явно указывает tf в алерте
            "spread_points": 12.0,         # float|None
            "spread_median_points": 9.0,   # float|None
            "bar_gap": False,              # bool|None — посчитанная аномалия разрыва
            "tick_stale": False,           # bool|None — посчитанная аномалия свежести тика
        },
    },
    "positions": {                         # только ОТКРЫТЫЕ позиции, ключ — ticket (int)
        123456: {
            "r_multiple": 0.8,              # float|None — прогресс в R (отрицательный = просадка)
            "opened_utc": dt.datetime(...), # datetime|None
            "beyond_sl": False,              # bool|None — цена уже за стопом, позиция ещё жива
        },
    },
    "gate_verdict": "OK",                   # str|None — вердикт risk_gate.py (OK/THROTTLE/HALT_NEW/FORCE_FLAT)
    "session_phase": "LONDON",              # str|None — ярлык из cfg.session.phases
    "news_windows": [                       # list|None — предстоящие новости
        {"name": "NFP", "minutes_until": 42.0},
    ],
    "last_event_utc": dt.datetime(...),     # datetime|None — момент последнего события
                                             #   (любого типа); None = событий ещё не было
}
```

**Явно для автора задачи 3.2**: `symbols[s].atr` и `symbols[s].atr_pctile` —
ОДНО значение на символ, не словарь по таймфреймам, хотя `perceive.py`
(`compute_tf_features`) считает ATR/ATR-перцентиль **отдельно для каждого
ТФ** и естественным было бы протащить эту структуру в `ctx` как есть. Это
осознанное упрощение контракта 3.1, не пропуск: ни один тип алерта из
таблицы ниже, кроме `trend_flips`, не указывает `tf` как поле — значит
`evaluate()` не может знать, ATR какого таймфрейма сравнивать с порогом
`price_touch.tolerance_atr`/`atr_pctile_above.level`, и просить его
угадывать было бы тем самым "угадыванием при нехватке данных", которое этот

таймфрейма — контракт этого не предусматривает: либо расширять таблицу
типов новым полем `tf` (как у `trend_flips`), либо задача 3.2 сама решает,
какой ТФ считать "эталонным", и кладёт в `ctx["symbols"][s]["atr"]` именно
его — но это её явное решение, а не то, что можно обнаружить отладкой

## `event_budget(events_today, cfg_alerts, *, now, last_event_ts, last_critical_event_ts, recent_event_ts) -> dict`

Три независимых яруса (см. разбор инцидента выше за тем, почему их три, а
не один):

```python
{"allowed": bool, "reason": str, "events_left": int,             # normal
 "critical_allowed": bool, "critical_reason": str,                # critical
 "hard_cap_remaining": int, "hard_cap_reason": str}                # оба яруса
```

1. **normal** (`allowed`/`reason`/`events_left`) — от `events_today` и
   `last_event_ts`:
   - `events_today >= cfg.max_events_per_day` → `allowed=False`, `events_left=0`.
   - иначе, если `last_event_ts` задан и `(now - last_event_ts).seconds < cfg.min_seconds_between_events`
     → `allowed=False` (`events_left` = структурный остаток, не зависит от причины блокировки).
   - иначе `allowed=True`.
2. **critical** (`critical_allowed`/`critical_reason`) — от `last_critical_
   event_ts` и `cfg.min_seconds_between_critical_events` ТОЛЬКО. Дневной
   лимит `max_events_per_day` в этот расчёт не входит вовсе — это
   единственное, что критический приоритет обходит.
3. **абсолютный потолок** (`hard_cap_remaining`/`hard_cap_reason`) — от
   `recent_event_ts` (итерируемое datetime всех доставленных событий любого
   приоритета за последние ~минуты): окно 60 секунд отфильтровывается внутри
   `event_budget`, `hard_cap_remaining = max(0, cfg.max_events_per_minute -
   count_in_window)`. Общий для normal и critical, не обходит никто.

`events_left = max(0, max_events_per_day - events_today)` — независимо от
причины отказа normal-яруса: дневной лимит и минимальный интервал — два
разных вопроса ("сколько ещё сегодня" vs "не рано ли для следующего"), их
числа не должны путаться друг с другом. По той же логике normal и critical
не должны путать СВОИ интервалы местами — `test_critical_respects_own_
shorter_interval` в тестах проверяет это явно на конфиге, где два интервала
намеренно разные (60с/15с), а не совпадают случайно.

`cfg_alerts` принимается и как `dict`, и как `cfg.alerts` (dataclass
`Alerts` из `config.py`) — ключи читаются напрямую (без `.get` с дефолтом),
опечатка в конфиге обязана падать громко, тот же принцип, что и в
`risk_gate.py._limit_picker`.

`evaluate()` использует **уже посчитанные** `budget["allowed"]`/
`budget["critical_allowed"]`/`budget["hard_cap_remaining"]` — сама
`evaluate()` не считает бюджет и не знает про `events_today`/`recent_event_
ts`/интервалы; вызывающий (задача 3.2) считает `event_budget(...)` один раз
в начале тика и передаёт результат. Внутри `evaluate()`:
- `priority="normal"` подчиняется `budget["allowed"]` безусловно;
- `priority="critical"` подчиняется `budget["critical_allowed"]` (свой ярус),
  игнорирует только `budget["allowed"]` (дневной лимит normal);
- ОБА приоритета расходуют `hard_cap_remaining` — `evaluate()` держит
  локальный счётчик и декрементирует его на каждое фактическое срабатывание
  ВНУТРИ одного вызова, поэтому потолок работает и для одновременной пачки
  в одном тике, не только между тиками.

`event_budget` не читает журнал сама — `events_today`/`last_event_ts`/
`last_critical_event_ts`/`recent_event_ts` считает вызывающий (задача 3.2)
по журналу (`append_alert_event`). ВАЖНО: события, доставленные с
`priority="critical"`, не должны попадать в `events_today` (это счётчик
только normal-яруса), но обязаны попадать в `recent_event_ts` (потолок
общий для обоих приоритетов).

### Три вида состояния для `event_budget` — обязанность вызывающего, не дефолт

`event_budget` не хранит состояние между вызовами (она чистая, как и
`evaluate`) — весь событийный контекст приходит аргументами. Вызывающий
(датчик задачи 3.2, и **только он**: это единственный процесс, который
будет звать `event_budget` в проекте) обязан вести и передавать **три
отдельных вида состояния** на каждом тике:

1. **`last_event_ts`** — момент последнего доставленного **normal**-события.
2. **`last_critical_event_ts`** — момент последнего доставленного
   **critical**-события. Отдельно от normal: смешать их значило бы вернуть
   ровно ту ошибку, которую чинил предыдущий фикс (см. разбор инцидента
   выше) — critical снова подчинялся бы normal-интервалу либо наоборот.
3. **`recent_event_ts`** — метки времени **всех** доставленных событий
   (любого приоритета) за последнюю минуту-полторы (окно 60с отфильтровывает
   сам `event_budget`).

Все три обновляются датчиком ПОСЛЕ того, как событие реально доставлено
(появилось в `fired` из `evaluate()` — не просто было истинным условием),
и должны переживать перезапуск датчика так же, как состояние `_state`
алертов (обычный источник восстановления — журнал, `append_alert_event`).

**Это требование к датчику 3.2, а не рекомендация.** У `last_critical_
event_ts` и `recent_event_ts` **намеренно нет дефолтов** — оба являются
обязательными keyword-only параметрами `event_budget`, вызов без любого из
них падает `TypeError` (тесты `test_event_budget_requires_last_critical_
event_ts` / `test_event_budget_requires_recent_event_ts`). Дефолты здесь
были опробованы (`None` и `()`) и вскрыли дефект: при проверке предыдущего
фикса вызов `event_budget(today, cfg.alerts, now=t, last_event_ts=last)`
(без двух новых параметров) остался валидным благодаря дефолтам и **тихо
вернул именно тот дефект, который фикс должен был закрыть** — 10
срабатываний за 10 секунд, потому что `last_critical_event_ts=None`
читалось как «критических событий ещё не было» (интервал не применяется), а
`recent_event_ts=()` — как «за минуту событий не было» (потолок не
срабатывает). Забывчивость вызывающего трактовалась как «ограничивать
нечего» — прямо противоположно принципу, на котором стоит весь пакет
(`risk_gate` при ошибке — `HALT_NEW`, `journal` отказывается писать
неполную запись, `evaluate` молчит при нехватке данных в `ctx`, а не
угадывает). Это тот же класс дефекта, что уже встречался в этом пакете:
инвариант, живущий в договорённости между модулями, а не в проверке — если
автор 3.2 передаст два параметра из трёх, всё будет работать и тесты
останутся зелёными, а защита механизма пробуждения будет молча выключена.

**НЕ возвращай дефолты `last_critical_event_ts=None`/`recent_event_ts=()`
обратно ради удобства вызова** — если понадобится «упростить» сигнатуру,
это тот самый компромисс, который уже один раз тихо сломал систему; чинить
неудобство вызова нужно на стороне вызывающего (например, обёрткой в 3.2,
которая сама ведёт три счётчика и не может забыть их передать — см.
следующий абзац), а не ослаблением этой функции.

**Открытый вопрос, требующий ответа владельца счёта, не решён в одностороннем
порядке**: было бы чище отдать ведение этих трёх счётчиков не трём
голым datetime-переменным в коде датчика, а объекту-леджеру
(`EventLedger` или похожему), который сам накапливает состояние по мере
доставки событий, восстанавливается из журнала при старте и отдаёт готовые
`last_event_ts`/`last_critical_event_ts`/`recent_event_ts` без риска забыть
один из трёх при вызове `event_budget`. Это расширение контракта, на
который начнёт опираться задача 3.2, поэтому оно НЕ реализовано здесь до
отдельного решения — датчик 3.2 пока обязан вести три значения вручную,
следуя этому разделу буквально.

# Протокол вооружения датчика (задача 3.3)

## Как запускается

```
Monitor(
  command: "python ~/.claude/trader-lib/scripts/alert_watch.py",
  description: "торговые алерты: уровни гипотез, режим, позиции, новости, стены",
  persistent: true
)
```

Фолбэк, если `Monitor` недоступен: `Bash(..., run_in_background: true)` с
`--max-ticks N`; при выходе команды модель пере-вызывается и взводит датчик заново.

Флаги CLI ровно два: `--config <путь>` и `--max-ticks <N>` (по умолчанию — до
остановки). Отдельного `--single-shot` нет: одиночный проход — это `--max-ticks 1`.

Датчик отказывается стартовать без исполнителя (`trader_lib/execute.py`, задача
4.1): «датчик без стоп-крана» стал бы вторым путём мимо правила.

## Взводится один раз за сессию

Условия меняются переписыванием `alerts.json` — датчик замечает изменение файла
(mtime+размер) и перечитывает его сам. Перезапуск ради новых условий — ошибка:
теряются состояния событийного бюджета (они восстанавливаются из
`alert_events.jsonl`, но повторный старт обнуляет очередь недоставленного).

Датчик сам дописывает в `alerts.json` поле `_state` (разоружение, память
пересечений). Он пишет файл, только если `_state` изменился И файл на диске не
менялся с момента его загрузки — иначе тик, начавшийся до того, как модель
переписала условия, затёр бы их своим старым снимком.

## Что приходит модели: строка события

Одна строка JSON в stdout на событие. Ключи, на которые модель имеет право
опираться:

| Поле | Смысл |
|------|-------|
| `event` | `alert` (условие модели) или `stop_valve` (действие кода) |
| `alert_id`, `alert_type`, `priority` | что сработало; `critical` = требует внимания сейчас |
| `fired_utc` | момент срабатывания |
| `symbol`, `ticket` | к чему относится (может быть `null`) |
| `snapshot` | счёт, стены, вердикт гейта, данные символа на момент события |
| `action` | ЧТО КОД СДЕЛАЛ С ДЕНЬГАМИ (только у `stop_valve`) |
| `delayed_report` | `true` → рассказ отложенный, действие произошло раньше |
| `original_fired_utc`, `delayed_by_seconds`, `suppressed_repeats` | у отложенного рассказа |

`delayed_report: true` — **не второе действие**. Это сообщение о том, что уже
случилось, придушенное событийным бюджетом и досланное, когда бюджет открылся.
Позиции, о которой в нём речь, может уже не быть — именно поэтому сообщение и
досылается: иначе о закрытии никто бы не рассказал.

## Что читает модель между событиями: `watch_heartbeat.json`

| Поле | Смысл |
|------|-------|
| `ts` | момент последней ПОДТВЕРЖДЁННОЙ проверки стены |
| `tick_utc` | пульс процесса (обновляется всегда) |
| `walls_checked` | считалась ли стена в этом тике |
| `pending_undelivered`, `pending_undelivered_ids` | сколько рассказов о действиях ждут доставки |
| `equity`, `daily_loss_pct`, `total_loss_pct`, `wall_breached` | стены |
| `gate_verdict`, `positions`, `unprotected`, `orphans` | состояние счёта |
| `events_today`, `events_last_minute`, `last_event_utc` | расход событийного бюджета |
| `errors` | отказы этого тика |

**Правило 90 секунд: `ts` старше 90 с → модель считает себя незащищённой и
новых входов не делает.** `ts` — свежесть ЗАЩИТЫ, а не процесса: живой датчик
со сломанным расчётом стены обязан выглядеть мёртвым. `tick_utc` при этом
свежий, и это НЕ основание считать себя защищённой.

## Очередь недоставленного

Сообщение о состоявшемся действии деньгами (закрытие по стене, восстановление
или закрытие позиции без стопа — включая НЕУДАЧНЫЕ попытки) не теряется, даже
если событийный бюджет придушил его в момент действия: оно встаёт в очередь и
досылается, когда бюджет откроется. Придушенные алерты по цене в очередь не
идут — их условие сработает снова само.

Практическое следствие для модели: **`pending_undelivered > 0` означает, что с
деньгами уже что-то сделано, а подробностей тебе ещё не рассказали.** Новых
входов при этом не делай — сначала дождись рассказа или прочитай
`alert_events.jsonl` сама.


## Поле `tf` у `atr_pctile_*` — почему появилось (2026-08-03)

Раздел выше объяснял, что ATR хранится ОДНИМ значением на символ, а выбор
эталонного таймфрейма оставлен потребителю, и предупреждал: это решение «не то,
что можно обнаружить отладкой постфактум».

Ровно так его и обнаружили. Датчик выбрал `DEFAULT_TIMEFRAMES[0]` = **M5** —
выбор, сделанный до того, как команда приняла стандарт **H1**. Трейдер видит в
снимке `perceive.py --tf H1` число одного таймфрейма, ставит от него порог, а
датчик сравнивает с другим. Ничто в момент постановки об этом не сообщает.

Цена стала предметной в первый же живой день команды. Трейдер `range` нашла на
USDCHF подтверждённый бокс (сопротивление тестировано трижды, поддержка
четырежды за девять часов) и завела единственное за день условие, способное
привести к сделке: «ATR сожмётся → тот же бокс даст R:R ≥ 1.5 без движения
цены». Порог 0.75 от H1-перцентиля 0.94 сгорел в ту же секунду — на M5 было
0.31. Она даже написала предупреждение про M5 в ноте соседнего алерта: знала о
пробеле и всё равно не могла его обойти, выразить H1 было нечем.

**Контракт теперь:** `tf` необязателен. Без него — эталонный перцентиль датчика,
как раньше (уже взведённые алерты не меняют смысл молча). С ним — перцентиль
именно этого ТФ из `atr_pctile_by_tf`, и он попадает в `detail` события, чтобы
на срабатывании было видно, что именно сравнивалось.

Запрошенного ТФ нет в контексте → алерт **пропускается с причиной**, а не
подставляет эталонный. Молча ответить числом другого таймфрейма — ровно тот
отказ, ради устранения которого поле и заводилось.
